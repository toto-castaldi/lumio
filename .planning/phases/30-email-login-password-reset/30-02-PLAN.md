**UpdatePasswordScreen:**

Create a two-phase screen: first OTP entry, then new password entry.

**Phase 1 — OTP Entry:**
- Title: `t('auth.updatePassword.title')` — "Set New Password"
- Subtitle: "Enter the 6-digit code sent to {email}"  — reuse `t('auth.otp.subtitle')` with email from route params
- 6-digit OTP input: Replicate the exact same pattern from OtpVerificationScreen (6 TextInputs with auto-advance, auto-submit, paste support, backspace navigation, shake animation on error). Copy the OTP input logic from OtpVerificationScreen.
- On OTP completion, call `verifyRecoveryOtp(email, code)` from AuthContext
- On success (no error thrown), transition to Phase 2 (password entry)
- On error: shake animation + clear digits (same as OtpVerificationScreen)
- Resend button with 60s cooldown: calls `resetPassword(email)` to resend recovery code

**Phase 2 — New Password:**
- Show new password TextInput with eye toggle (same pattern as LoginScreen/SignUpScreen)
- Client-side validation: minimum 6 characters
- "Update password" button: `t('auth.updatePassword.update')`
- On tap: call `updatePassword(newPassword)` from AuthContext
- updatePassword (from Plan 01) already handles: update user → global signOut → reset recoveryState to idle
- After updatePassword completes successfully: show toast with `t('auth.updatePassword.success')` / `t('auth.updatePassword.successDescription')`
- The global signOut + recoveryState='idle' will trigger AppNavigator to show LoginScreen automatically
- On error: show inline error message. If error contains 'same_password' or similar, show `t('auth.updatePassword.samePassword')`

**State management:**
- `phase` state: `'otp' | 'password'`
- OTP digit state: array of 6 strings (same as OtpVerificationScreen)
- Password state, showPassword toggle
- Loading from AuthContext: `verifyRecoveryLoading`, `updatePasswordLoading`

**Screen type:** NativeStackScreenProps<AuthStackParamList, 'UpdatePassword'>

**Important:** Do NOT implement a confirm password field. CONTEXT.md says single password field is the pattern (same as SignUpScreen). The `auth.updatePassword.confirmPasswordLabel` and `passwordMismatch` i18n keys exist but should NOT be used per this decision.

**Consistent styling:** Match LoginScreen/SignUpScreen visual patterns exactly.
